# Laravel React Starter Kit｜Service + Repository 構成での実装フロー

> 対象: Laravel 13 系 React スターターキット（Inertia 3 / React 19 / TypeScript / Tailwind 4 / shadcn-ui / Wayfinder / Fortify）
> アーキテクチャ: **Controller → Service → Repository → Model**
> テスト: **PHPUnit**（Pest ではない）
> 題材: 「タスク（Task）」機能の一覧表示 + 作成

---

## 0. まず全体像：4層の責務を1枚で

```
┌──────────────────────────────────────────────────┐
│ Controller     HTTPの世界（受け取る・返す）           │
│  ↓ 「userId=3 のタスクを作って」と依頼               │
├──────────────────────────────────────────────────┤
│ Service        ビジネスロジック・トランザクション・副作用  │
│  ↓ 「このデータを保存して」と依頼                     │
├──────────────────────────────────────────────────┤
│ Repository     データの出し入れだけ（永続化の抽象化）     │
│  ↓ Eloquent を呼ぶ                                │
├──────────────────────────────────────────────────┤
│ Model          テーブル構造・リレーション               │
└──────────────────────────────────────────────────┘
```

**一方向にしか依存しない**のが鉄則です。Repository が Service を呼ぶ、Model が Repository を知っている、といったことは起きません。

### 各層の判断基準（迷ったらこの表）

| 書きたいこと | 置く場所 |
|---|---|
| リクエストの受け取り、リダイレクト先の決定 | Controller |
| 「入力値は正しい形か」 | FormRequest |
| 「このユーザーに権限があるか」 | Policy |
| 「作成したら通知を送る」「複数テーブルをまとめて更新」 | **Service** |
| 「未完了かつ期限切れのタスクを取ってくる」 | **Repository** |
| 「completed_at が null なら未完了」という属性の判定 | Model |
| 画面の見た目 | React (pages) |

# STEP 0：画面と props の「契約」を決める

コードを書く前の唯一の工程。ここを飛ばすと必ず手戻りします。

```
【画面】 タスク一覧
URL      : GET /tasks
page     : resources/js/pages/tasks/index.tsx
props    : { tasks: { id, title, dueAt, isDone }[] }

【画面】 タスク作成
URL      : POST /tasks
入力     : { title: 必須255文字, dueAt: 任意・未来日時 }
成功時   : /tasks へリダイレクト + フラッシュ「作成しました」
失敗時   : 同じページに戻る + errors に自動で入る
権限     : ログイン必須。自分のタスクしか見えない
```

**さらに Service/Repository 構成では、ここで「必要な問い合わせ」も洗い出します。**

```
【Repository に必要なメソッド】
- ユーザーの未完了タスクを新しい順に取得
- タスクを1件保存
```

これが STEP 6 のインターフェース定義にそのまま化けます。

# STEP 1：マイグレーション（データの器）

### 作り方：**コマンド**

```bash
php artisan make:model Task -mf
# -m … migration も同時生成
# -f … factory も同時生成
```

### 場所
`database/migrations/2026_08_06_000000_create_tasks_table.php`

```php
public function up(): void
{
    Schema::create('tasks', function (Blueprint $table) {
        $table->id();
        $table->foreignId('user_id')->constrained()->cascadeOnDelete();
        $table->string('title');
        $table->text('body')->nullable();
        $table->timestamp('due_at')->nullable();
        $table->timestamp('completed_at')->nullable();
        $table->timestamps();

        $table->index(['user_id', 'completed_at']);
    });
}
```

### コード解説

- `foreignId('user_id')->constrained()` … `users.id` への外部キーを自動生成。「このタスクは誰のものか」を**DB レベルで保証**する
- `cascadeOnDelete()` … ユーザー削除時にタスクも消える。孤児レコードを作らない
- `completed_at` を nullable にして完了フラグの代わりにする … `is_done` の boolean より「いつ完了したか」も残るので情報量が多い
- `index(['user_id', 'completed_at'])` … STEP 0 で洗い出した「ユーザーの未完了タスクを取る」クエリに合わせた複合インデックス。**必要な問い合わせを先に決めておくと、インデックスもこの時点で正しく張れます**

```bash
php artisan migrate
```

### 責務

> **データの形と制約だけ。** アプリのロジックは一切書かない。
> ここが揺れると全工程がやり直しになるので、nullable か否か・外部キーを張るかは**この時点で真剣に決める**。

# STEP 2：Model（テーブルと PHP の橋渡し）

### 作り方：STEP 1 で**自動生成済み**。中身を手で書く

### 場所
`app/Models/Task.php`

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\BelongsTo;

class Task extends Model
{
    use HasFactory;

    protected $fillable = ['user_id', 'title', 'body', 'due_at'];

    protected function casts(): array
    {
        return [
            'due_at'       => 'datetime',
            'completed_at' => 'datetime',
        ];
    }

    public function user(): BelongsTo
    {
        return $this->belongsTo(User::class);
    }

    public function isDone(): bool
    {
        return $this->completed_at !== null;
    }
}
```

### コード解説

- `$fillable` … 一括代入を許すカラムのホワイトリスト。**Repository 構成では `user_id` を含めます**。Action 構成では `$user->tasks()->create()` とリレーション経由で暗黙に入れていましたが、Repository は「渡された配列を保存する」のが仕事なので、`user_id` を明示的に受け取る形にします（その代わり、**`user_id` を誰が決めるかは Service が責任を持つ** → STEP 9 参照）
- `casts()` … DB の文字列を `Carbon` に自動変換。これがないと `$task->due_at->format(...)` が動かない
- `isDone()` … 「completed_at が null でなければ完了」というルールをモデルに集約。Controller や React に同じ判定を散らばらせない

### 責務

> **データの構造・関連・そのレコード自身についての判断だけ。**
> クエリの組み立て（→ Repository）、副作用（→ Service）、権限（→ Policy）はここに書かない。

# STEP 3：Factory（テストデータの型紙）

### 作り方：STEP 1 で**自動生成済み**。中身を手で書く

### 場所
`database/factories/TaskFactory.php`

```php
public function definition(): array
{
    return [
        'user_id'      => User::factory(),
        'title'        => fake()->realText(20),
        'body'         => fake()->optional()->realText(60),
        'due_at'       => fake()->dateTimeBetween('+1 day', '+1 month'),
        'completed_at' => null,
    ];
}

public function done(): static
{
    return $this->state(fn () => ['completed_at' => now()]);
}
```

### コード解説

- `'user_id' => User::factory()` … Task を作ると User も**連鎖生成**される。`Task::factory()->create()` 1行で関連込みのデータが揃う
- `done()` は **state メソッド**。`Task::factory()->done()->create()` で完了済みタスクが作れる。テストの意図がコードから読める

### 責務

> **意味のあるダミーデータの作り方を一箇所に集める。**
> 初学者が最も飛ばしがちですが、**ここを書くと以降の作業時間が半分になります**。テストでも `php artisan tinker` でも1行でデータが用意できるようになるからです。

# STEP 4：Feature テスト（PHPUnit）

### 作り方：**コマンド**（`--phpunit` を付けるのが重要）

```bash
php artisan make:test TaskTest --phpunit
```

> スターターキットの初期状態が Pest の場合、このフラグなしだと Pest 形式の雛形が出ます。プロジェクト全体を PHPUnit に揃えるなら `phpunit.xml` と `tests/TestCase.php` がそのまま使えるので、あとは書き方をクラス形式に統一するだけです。

### 場所
`tests/Feature/TaskTest.php`

```php
<?php

namespace Tests\Feature;

use App\Models\Task;
use App\Models\User;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Inertia\Testing\AssertableInertia as Assert;
use PHPUnit\Framework\Attributes\Test;
use Tests\TestCase;

class TaskTest extends TestCase
{
    use RefreshDatabase;

    private User $user;

    protected function setUp(): void
    {
        parent::setUp();

        $this->user = User::factory()->create();
    }

    #[Test]
    public function ログインユーザーは自分のタスク一覧を見られる(): void
    {
        Task::factory()->for($this->user)->create(['title' => '牛乳を買う']);
        Task::factory()->create(['title' => '他人のタスク']);

        $this->actingAs($this->user)
            ->get('/tasks')
            ->assertOk()
            ->assertInertia(fn (Assert $page) => $page
                ->component('tasks/index')
                ->has('tasks', 1)
                ->where('tasks.0.title', '牛乳を買う')
            );
    }

    #[Test]
    public function タスクを作成できる(): void
    {
        $this->actingAs($this->user)
            ->post('/tasks', ['title' => 'パンを買う'])
            ->assertRedirect('/tasks')
            ->assertSessionHas('success');

        $this->assertDatabaseHas('tasks', [
            'user_id' => $this->user->id,
            'title'   => 'パンを買う',
        ]);
    }

    #[Test]
    public function タイトルが空なら作成できない(): void
    {
        $this->actingAs($this->user)
            ->post('/tasks', ['title' => ''])
            ->assertInvalid(['title']);

        $this->assertDatabaseCount('tasks', 0);
    }

    #[Test]
    public function 未ログインならログイン画面にリダイレクトされる(): void
    {
        $this->get('/tasks')->assertRedirect('/login');
    }
}
```

### コード解説（PHPUnit 特有の点）

- `use RefreshDatabase;` … 各テストの前後で DB をマイグレーション＋ロールバック。テスト同士がデータで干渉しなくなる。**忘れると原因不明の失敗が多発する**ので必ず付ける
- `#[Test]` 属性（PHP 8 の Attribute）… メソッド名を `test_` で始めなくてもテストとして認識される。おかげで**日本語のメソッド名が使えて、テスト結果が仕様書のように読める**
  - 属性を使わない場合は `public function test_タスクを作成できる(): void` と `test_` プレフィックスを付ける
- `setUp()` … 全テスト共通の前準備。`parent::setUp()` を最初に呼ぶのを忘れないこと
- `private User $user` … プロパティに保持することで各テストが短くなる

### Inertia 特有の点（API との最大の違い）

- `assertInertia()` … JSON ではなく「**どのページに、どんな props が渡ったか**」を検証する
- `->component('tasks/index')` … `Inertia::render()` に渡した文字列と一致するか
- `->has('tasks', 1)` … props の `tasks` が1件か。**他人のタスクが混ざっていないこと**をここで保証している
- `assertRedirect` … API なら 201 + JSON だが、**Inertia はリダイレクトが正常系**
- `assertInvalid` … バリデーションエラーはセッション経由で props の `errors` に入るので、ステータス 422 ではなくこちらで検証

### 責務

> **「この機能が完成したと言える条件」を、実装より先に固定する。**
>
> 先に書く理由は「真面目だから」ではなく **「楽だから」**。ブラウザでログイン → 入力 → 送信…という手動確認ループが消えます。STEP 0 の契約をそのまま写すだけなので、実は一番書きやすいタイミングでもあります。
>
> この時点では全部**真っ赤に落ちます**。それが正しい状態です。

# STEP 5：ルーティング（URL の宣言）

### 作り方：**手動追記**

### 場所
`routes/web.php`（★ `api.php` ではない）

```php
use App\Http\Controllers\TaskController;

Route::middleware(['auth', 'verified'])->group(function () {
    Route::get('dashboard', fn () => Inertia::render('dashboard'))->name('dashboard');

    Route::resource('tasks', TaskController::class);
});
```

### コード解説

- `Route::resource` … index / create / store / show / edit / update / destroy の**7ルートを一括定義**。Inertia は画面遷移も Laravel のルートを使うので、`create`（フォーム画面）や `edit` も必要になる点が API との違い
- 絞るなら `->only(['index', 'create', 'store'])`
- `middleware(['auth', 'verified'])` … Fortify が用意した認証。未ログインなら自動で `/login` へ

```bash
php artisan route:list --path=tasks
```

### Wayfinder が裏で TypeScript を生成する

```bash
php artisan wayfinder:generate    # npm run dev 実行中なら自動
```

生成物：
```
resources/js/actions/App/Http/Controllers/TaskController.ts
resources/js/routes/tasks/index.ts
```

これで React 側は **URL 文字列を一切書かなくなります**：

```ts
import TaskController from '@/actions/App/Http/Controllers/TaskController';

TaskController.index();            // { url: '/tasks', method: 'get' }
TaskController.store();            // { url: '/tasks', method: 'post' }
TaskController.show({ task: 1 });  // { url: '/tasks/1', method: 'get' }
```

> 自動生成ディレクトリは毎回作り直されるので、手で編集しない・gitignore 対象（キットでは設定済み）。
> Wayfinder は現在 beta（v0.1.x）で、次期版では import パスが `@/wayfinder/...` に変わる予定です。実際の生成先を一度確認してください。

### 責務

> **どの URL がどのコントローラのどのメソッドに繋がるかの一覧表。**
> ここに条件分岐やロジックを書かない。`web.php` を見れば**アプリの機能一覧が読める**状態を保つ。

# STEP 6：Repository Interface（「何ができるか」の宣言）★

**ここから Service/Repository 構成の本体です。**

### 作り方：**手動作成**（ディレクトリごと自分で作る）

```bash
mkdir -p app/Repositories/Contracts app/Repositories/Eloquent
```

### 場所
`app/Repositories/Contracts/TaskRepositoryInterface.php`

```php
<?php

namespace App\Repositories\Contracts;

use App\Models\Task;
use Illuminate\Support\Collection;

interface TaskRepositoryInterface
{
    /**
     * 指定ユーザーの未完了タスクを新しい順に取得する。
     *
     * @return Collection<int, Task>
     */
    public function getPendingByUserId(int $userId): Collection;

    /**
     * タスクを1件作成する。
     *
     * @param  array<string, mixed>  $attributes
     */
    public function create(array $attributes): Task;

    public function findById(int $id): ?Task;
}
```

### コード解説

- **実装（`class`）ではなく契約（`interface`）を先に書く**のがポイント。「Eloquent でどう書くか」を考える前に、「アプリはこのデータについて何を必要としているか」だけを決める
- メソッド名は **業務の言葉**にする。`where('completed_at', null)->orderBy(...)` という**実装の詳細を名前に出さない**
  - ✅ `getPendingByUserId()` … 「未完了タスクをくれ」という業務要求
  - ❌ `whereCompletedAtNullOrderByCreatedAtDesc()` … Eloquent が漏れ出している
- `@return Collection<int, Task>` … PHPDoc のジェネリクス記法。IDE の補完と静的解析（Larastan）が効くようになる。**Repository は返り値の型が曖昧になりがちなので、ここを丁寧に書くと後が楽**
- 返り値に `Builder`（クエリビルダ）を**返さない**。返してしまうと呼び出し側で `->where()` を続けられてしまい、Repository で隠したはずの Eloquent が Service に漏れます

### 責務

> **「このアプリはタスクというデータについて、何を必要としているか」の一覧。**
>
> ここには SQL も Eloquent も一切登場しません。MySQL だろうと外部 API だろうと、**この契約さえ満たせば差し替え可能**、という状態を作るのが目的です。

# STEP 7：Repository 実装（「どうやるか」）★

### 作り方：**手動作成**

### 場所
`app/Repositories/Eloquent/EloquentTaskRepository.php`

```php
<?php

namespace App\Repositories\Eloquent;

use App\Models\Task;
use App\Repositories\Contracts\TaskRepositoryInterface;
use Illuminate\Support\Collection;

class EloquentTaskRepository implements TaskRepositoryInterface
{
    public function __construct(
        private readonly Task $model,
    ) {}

    public function getPendingByUserId(int $userId): Collection
    {
        return $this->model
            ->newQuery()
            ->where('user_id', $userId)
            ->whereNull('completed_at')
            ->latest()
            ->get();
    }

    public function create(array $attributes): Task
    {
        return $this->model->newQuery()->create($attributes);
    }

    public function findById(int $id): ?Task
    {
        return $this->model->newQuery()->find($id);
    }
}
```

### コード解説

- `implements TaskRepositoryInterface` … 契約を守っていることを PHP に保証させる。メソッドを書き忘れたら**実行前にエラーになる**
- `private readonly Task $model` … コンストラクタプロパティプロモーション（PHP 8）。`Task::query()` と静的に呼ぶより、**注入したほうがテストで差し替えやすい**
- `newQuery()` … 毎回まっさらなクエリビルダを取得。同じインスタンスに条件が蓄積する事故を防ぐ
- クラス名を `EloquentTaskRepository` にしている … 「Eloquent 版の実装」であることが名前でわかる。将来 `InMemoryTaskRepository`（テスト用）や `ApiTaskRepository` を足すときに自然に並ぶ

### 責務（★ここを間違えると Repository を作る意味が消える）

> **データの出し入れだけ。**
>
> **Repository に書いてはいけないもの：**
> - ❌ `DB::transaction()` … トランザクションの範囲を決めるのは Service の仕事。Repository は「1つの操作」の単位でしかない
> - ❌ メール送信・通知・イベント発火 … 副作用は Service
> - ❌ 権限チェック … Policy
> - ❌ 「タイトルが空なら例外」などの業務ルール … Service
> - ❌ `Auth::user()` の参照 … Repository は「今誰がログインしているか」を知らなくてよい。必要な `userId` は引数で受け取る

# STEP 8：ServiceProvider でバインドする ★

**interface は自分では動きません。「この契約にはこの実装を使う」と Laravel に教える工程が必須です。** ここを忘れると `Target [TaskRepositoryInterface] is not instantiable.` というエラーが出ます（Repository 構成で最頻出のつまずきポイント）。

### 作り方：**コマンド**

```bash
php artisan make:provider RepositoryServiceProvider
```

> Laravel 11 以降は `bootstrap/providers.php` に**自動で登録されます**（昔の `config/app.php` の providers 配列は廃止）。生成後に一度ファイルを開いて登録されているか確認しておくと安心です。

### 場所
`app/Providers/RepositoryServiceProvider.php`

```php
<?php

namespace App\Providers;

use App\Repositories\Contracts\TaskRepositoryInterface;
use App\Repositories\Eloquent\EloquentTaskRepository;
use Illuminate\Support\ServiceProvider;

class RepositoryServiceProvider extends ServiceProvider
{
    /**
     * interface => 実装 の対応表
     *
     * @var array<class-string, class-string>
     */
    public array $bindings = [
        TaskRepositoryInterface::class => EloquentTaskRepository::class,
    ];
}
```

### コード解説

- `$bindings` プロパティ … `register()` の中で `$this->app->bind(...)` を書くのと同じですが、**対応表として一覧性が高い**のでこちらを推奨
- これにより、以降どこかで `TaskRepositoryInterface` を型宣言すると、Laravel が自動で `EloquentTaskRepository` のインスタンスを注入してくれます

確認：
```bash
php artisan about        # 登録済みプロバイダが見える
```

### 責務

> **「抽象」と「具象」の結線表。**
> このファイルがあることで、Service は `EloquentTaskRepository` という具体的なクラス名を**一度も書かずに済みます**。テストのときだけモックに差し替える、といったことが可能になるのはこの1行のおかげです。

# STEP 9：Service（ビジネスロジックの本体）★

### 作り方：**手動作成**

```bash
mkdir -p app/Services
```

### 場所
`app/Services/TaskService.php`

```php
<?php

namespace App\Services;

use App\Models\Task;
use App\Models\User;
use App\Repositories\Contracts\TaskRepositoryInterface;
use Illuminate\Support\Collection;
use Illuminate\Support\Facades\DB;

class TaskService
{
    public function __construct(
        private readonly TaskRepositoryInterface $taskRepository,
    ) {}

    /**
     * ダッシュボードに表示する未完了タスクを取得する。
     *
     * @return Collection<int, Task>
     */
    public function getPendingTasksFor(User $user): Collection
    {
        return $this->taskRepository->getPendingByUserId($user->id);
    }

    /**
     * タスクを作成する。
     *
     * @param  array<string, mixed>  $attributes
     */
    public function create(User $user, array $attributes): Task
    {
        return DB::transaction(function () use ($user, $attributes) {
            $task = $this->taskRepository->create([
                ...$attributes,
                'user_id' => $user->id,   // 所有者は必ずサーバー側で決める
            ]);

            // 副作用（通知・イベント・ログ）はここに集約する
            // TaskCreated::dispatch($task);

            return $task;
        });
    }
}
```

### コード解説

- **コンストラクタで `TaskRepositoryInterface` を型宣言している** … 具象クラスではなく契約に依存する。STEP 8 のバインドにより、実行時には `EloquentTaskRepository` が入る。**テストではモックに差し替えられる**（→ STEP 10）
- `'user_id' => $user->id` を Service で付ける … ここが**セキュリティ上の要**。Controller から渡された `$attributes` に `user_id` が混ざっていても、後から上書きするので他人名義のタスクは作れません。**「所有者を決めるのはサーバー」というルールを一箇所に固定する**
- `DB::transaction()` … 途中で失敗したら全部巻き戻す。**トランザクションの境界は Service が決める**。複数の Repository をまたぐ処理が出てきたとき、この設計が効いてきます
- `getPendingTasksFor()` は Repository をそのまま呼んでいるだけ … 今は「無駄な中継」に見えますが、**あとで「期限切れは先頭に並べる」「上限20件」などの業務ルールが加わる場所**として空けておきます

### 責務

> **この機能が「やること」そのもの。ドメインロジックを持つ唯一の層。**
>
> **Service に書いてはいけないもの：**
> - ❌ `$request` の参照 … HTTP を知らないから、コマンドからもキューからも同じロジックが呼べる
> - ❌ `Task::where(...)` の直接記述 … クエリは Repository へ
> - ❌ `Inertia::render()` / `redirect()` … 画面のことは Controller へ

# STEP 10：Service の単体テスト（PHPUnit）★

**Repository 構成の最大の見返りがここで回収されます。DB を一切使わずに Service のロジックを検証できます。**

### 作り方：**コマンド**

```bash
php artisan make:test Services/TaskServiceTest --unit --phpunit
```

### 場所
`tests/Unit/Services/TaskServiceTest.php`

```php
<?php

namespace Tests\Unit\Services;

use App\Models\Task;
use App\Models\User;
use App\Repositories\Contracts\TaskRepositoryInterface;
use App\Services\TaskService;
use Illuminate\Support\Facades\DB;
use PHPUnit\Framework\Attributes\Test;
use Tests\TestCase;

class TaskServiceTest extends TestCase
{
    #[Test]
    public function 作成時にログインユーザーのIDが必ず付与される(): void
    {
        $user = new User();
        $user->id = 7;

        $repository = $this->createMock(TaskRepositoryInterface::class);

        // ★ここが検証の本体：Repository に何が渡されたかを覗く
        $repository->expects($this->once())
            ->method('create')
            ->with($this->equalTo([
                'title'   => 'パンを買う',
                'user_id' => 7,
            ]))
            ->willReturn(new Task());

        // トランザクションはそのままコールバックを実行させる
        DB::shouldReceive('transaction')
            ->once()
            ->andReturnUsing(fn (callable $callback) => $callback());

        $service = new TaskService($repository);

        $service->create($user, ['title' => 'パンを買う']);
    }

    #[Test]
    public function 攻撃者がuser_idを偽装しても上書きされる(): void
    {
        $user = new User();
        $user->id = 7;

        $repository = $this->createMock(TaskRepositoryInterface::class);

        $repository->expects($this->once())
            ->method('create')
            ->with($this->callback(
                fn (array $attributes) => $attributes['user_id'] === 7
            ))
            ->willReturn(new Task());

        DB::shouldReceive('transaction')
            ->andReturnUsing(fn (callable $callback) => $callback());

        $service = new TaskService($repository);

        // 悪意ある user_id=999 を混ぜて呼ぶ
        $service->create($user, ['title' => '乗っ取り', 'user_id' => 999]);
    }
}
```

### コード解説

- `$this->createMock(TaskRepositoryInterface::class)` … **PHPUnit 標準のモック機能**。interface から偽物のオブジェクトを自動生成する。DB に一切触らない
- `expects($this->once())->method('create')` … 「`create` が**ちょうど1回**呼ばれること」を検証。呼ばれなければテスト失敗
- `->with($this->equalTo([...]))` … 「**その引数で**呼ばれること」を検証。ここで `user_id` が正しく付与されているかを見ている
- `$this->callback(fn (array $attributes) => ...)` … 引数の一部だけを検証したいときの書き方。柔軟な条件を書ける
- `DB::shouldReceive('transaction')` … `DB` ファサードを差し替え、渡されたクロージャをそのまま実行させる。**実 DB なしでトランザクション内のロジックが走る**
- `use RefreshDatabase` を**付けていない** … DB を使わないので不要。だからこのテストは**ミリ秒で終わります**

> 2つ目のテストが重要です。「user_id を偽装されても上書きされる」というセキュリティ要件を、**DB を立てずに数十行で検証できている**。これが Repository を interface で切った直接的な見返りです。

### 責務

> **Service のロジックだけを、周囲から切り離して検証する。**
>
> Feature テスト（STEP 4）が「全部つないで動くか」を見るのに対し、Unit テストは「**この判断は正しいか**」を見ます。両方あって初めて、壊れたときにどこが原因か即座にわかります。

```bash
php artisan test --testsuite=Unit      # 速い。開発中はこれを回す
php artisan test                       # 全部
```

# STEP 11：FormRequest（入力の門番）

### 作り方：**コマンド**

```bash
php artisan make:request StoreTaskRequest
```

### 場所
`app/Http/Requests/StoreTaskRequest.php`

```php
<?php

namespace App\Http\Requests;

use Illuminate\Foundation\Http\FormRequest;

class StoreTaskRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true;   // 認可は Policy に任せる（STEP 15）
    }

    /**
     * @return array<string, array<int, string>>
     */
    public function rules(): array
    {
        return [
            'title'  => ['required', 'string', 'max:255'],
            'body'   => ['nullable', 'string', 'max:2000'],
            'due_at' => ['nullable', 'date', 'after:now'],
        ];
    }

    public function attributes(): array
    {
        return [
            'title'  => 'タイトル',
            'due_at' => '期限',
        ];
    }
}
```

### コード解説

- `rules()` … 通過しなかったリクエストは**Controller に到達しない**
- `attributes()` … エラーメッセージの項目名を日本語化。React 側は `errors.title` をそのまま表示するだけでよくなる
- **Controller の中で `$request->validate()` を書かない**。分離すると「入力条件を知りたい」ときに見るファイルが1つに定まる

### Inertia でのエラーの流れ（全自動）

```
バリデーション失敗
  → Laravel が 422 ではなく「元のページへリダイレクト＋セッションに errors」
  → Inertia のミドルウェアが errors を props に詰める
  → React 側で errors.title がそのまま参照できる
```

**try-catch もエラーハンドリングも自分で書く必要がありません。**

### 責務

> **「そのリクエストは受け付けてよい形か」だけ。**
> 権限は Policy、保存は Service。混ぜない。

# STEP 12：Controller（薄い交通整理役）

### 作り方：**コマンド**

```bash
php artisan make:controller TaskController --resource
```

### 場所
`app/Http/Controllers/TaskController.php`

```php
<?php

namespace App\Http\Controllers;

use App\Http\Requests\StoreTaskRequest;
use App\Http\Resources\TaskResource;
use App\Services\TaskService;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Inertia\Inertia;
use Inertia\Response;

class TaskController extends Controller
{
    public function __construct(
        private readonly TaskService $taskService,
    ) {}

    public function index(Request $request): Response
    {
        $tasks = $this->taskService->getPendingTasksFor($request->user());

        return Inertia::render('tasks/index', [
            'tasks' => TaskResource::collection($tasks),
        ]);
    }

    public function create(): Response
    {
        return Inertia::render('tasks/create');
    }

    public function store(StoreTaskRequest $request): RedirectResponse
    {
        $this->taskService->create($request->user(), $request->validated());

        return to_route('tasks.index')->with('success', 'タスクを作成しました');
    }
}
```

### コード解説

- **コンストラクタで Service を注入** … Controller は Repository を**直接知りません**。層を飛び越えないことで、依存の向きが一方向に保たれます
- `Inertia::render('tasks/index', [...])` … 第1引数は `resources/js/pages/` からの相対パス（`.tsx` 不要、小文字）。第2引数が props
- `StoreTaskRequest` を型宣言するだけで**バリデーションが自動実行**される
- `to_route('tasks.index')` … API なら 201 + JSON だが、**Inertia はリダイレクトが正常系**。React 側は自動的に一覧を再取得する
- `->with('success', ...)` … フラッシュメッセージ。`HandleInertiaRequests` で共有 props に載せればトースト表示できる

### 責務

> **受け取る → Service に渡す → 画面を返す。理想は3行。**
> `if` が増えてきたら **Service に移すサイン**です。

# STEP 13：Resource + TypeScript 型（★Inertia の要）

### 13-1. PHP 側：Resource

#### 作り方：**コマンド**

```bash
php artisan make:resource TaskResource
```

#### 場所
`app/Http/Resources/TaskResource.php`

```php
<?php

namespace App\Http\Resources;

use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\JsonResource;

class TaskResource extends JsonResource
{
    /**
     * @return array<string, mixed>
     */
    public function toArray(Request $request): array
    {
        return [
            'id'     => $this->id,
            'title'  => $this->title,
            'body'   => $this->body,
            'dueAt'  => $this->due_at?->toIso8601String(),
            'isDone' => $this->isDone(),
        ];
    }
}
```

#### コード解説

- **モデルをそのまま props に渡さない。** `['tasks' => $tasks]` と書くと、後でカラムを追加したときに**意図せず内部情報がブラウザに漏れます**（props は HTML に埋め込まれ、DevTools で全部見えます）
- `dueAt` とキャメルケースに変換 … TypeScript の慣習に合わせる（統一が大事）
- `$this->due_at?->toIso8601String()` … null 安全演算子。日付は ISO8601 文字列で渡すと React 側で扱いやすい
- `isDone` … STEP 2 でモデルに書いた判定をここで呼ぶ。**React 側に `completed_at !== null` を書かせない**

### 13-2. TypeScript 側：型定義

#### 作り方：**手動追記**

#### 場所
`resources/js/types/index.d.ts`

```ts
export interface Task {
    id: number;
    title: string;
    body: string | null;
    dueAt: string | null;
    isDone: boolean;
}
```

### 責務（★核心）

> **Resource の `toArray()` と TS の `interface` は鏡合わせのペアです。**
>
> ```
> TaskResource::toArray()  ←→  interface Task
>       （PHP側の出口）           （TS側の入口）
> ```
>
> **片方を変えたら必ずもう片方も変える。** これが Inertia 開発の規律の9割。
> サボると「PHP で消したはずのプロパティを React が参照して落ちる」という、最も追いにくいバグが出ます。

import { Form, Head } from '@inertiajs/react';
import AppLayout from '@/layouts/app-layout';
import { Button } from '@/components/ui/button';
import { Input } from '@/components/ui/input';
import { Label } from '@/components/ui/label';

export default function Create() {

                            )}

                            {processing ? '保存中...' : '作成する'}
                        </Button>
                    </>

- `name="title"` … FormRequest の `rules()` のキーと一致させる。ここが唯一の接続点

> 動的なフィールド追加など複雑な制御が必要になったら `useForm()` に切り替えます。`<Form>` は `useForm` の置き換えではなく「簡単に書ける版」という位置づけ。

# まとめ：責務分離の全体マップ

| レイヤ | 場所 | 作り方 | 責務（一言で） | 書いてはいけないもの |
|---|---|---|---|---|
| Migration | `database/migrations/` | コマンド | データの形と制約 | ロジック |
| Model | `app/Models/` | コマンド＋手 | 構造・関連・レコード自身の判定 | クエリ組み立て、副作用 |
| Factory | `database/factories/` | コマンド＋手 | ダミーデータの型紙 | 本番ロジック |
| Feature Test | `tests/Feature/` | コマンド＋手 | 完成の定義（つないで動くか） | ― |
| Route | `routes/web.php` | 手動 | URL の一覧表 | 条件分岐 |
| **Repository Interface** | `app/Repositories/Contracts/` | 手動 | **必要なデータ操作の契約** | SQL、Eloquent |
| **Repository 実装** | `app/Repositories/Eloquent/` | 手動 | **データの出し入れだけ** | トランザクション、副作用、Auth |
| **ServiceProvider** | `app/Providers/` | コマンド＋手 | **抽象と具象の結線表** | ロジック |
| **Service** | `app/Services/` | 手動 | **機能の本体・トランザクション・副作用** | `$request`、直接クエリ、画面 |
| Unit Test | `tests/Unit/Services/` | コマンド＋手 | Service の判断が正しいか | DB アクセス |
| FormRequest | `app/Http/Requests/` | コマンド | 入力の門番 | 権限、保存処理 |
| Controller | `app/Http/Controllers/` | コマンド | 交通整理（3行） | ロジック、Repository 直呼び |
| Resource | `app/Http/Resources/` | コマンド＋手 | props の整形 | DB アクセス |
| TS 型 | `resources/js/types/` | 手動 | props の受け入れ契約 | ― |
| Page | `resources/js/pages/` | 手動 | 見た目と操作 | 計算、判定 |

# よくある失敗と対処

| 症状 | 原因 | 対処 |
|---|---|---|
| `Target [TaskRepositoryInterface] is not instantiable.` | ServiceProvider でバインドしていない | STEP 8 を確認。`bootstrap/providers.php` に登録されているかも見る |
| Repository が肥大化して 30 メソッドに | Controller の都合でメソッドを足し続けた | 業務単位で名前を付け直す。使われていないメソッドは消す |
| Service が Repository の薄いラッパーだけになった | 業務ルールがまだ無い | 問題なし。ルールが増える場所として空けておく |
| Repository のメソッドに `where` を追加したくなる | 呼び出し側の都合が漏れている | 引数を増やすのではなく、**業務の言葉で新しいメソッドを足す** |
| 単体テストで DB が必要になった | Service が Eloquent を直接触っている | クエリを Repository に移す |
| ページが真っ白 / 404 | `Inertia::render()` の文字列と `pages/` のパスが不一致 | 大文字小文字・階層を完全一致させる |
| `Cannot find module '@/actions/...'` | Wayfinder 未生成 | `php artisan wayfinder:generate` |
| props が `undefined` | Resource と TS 型がずれた | STEP 13 のペアを同時に直す |
| DevTools に余計な情報が見える | モデルを直接 props に渡した | 必ず Resource を挟む |
| テストが不安定・前のデータが残る | `RefreshDatabase` の付け忘れ | Feature テストには必ず付ける |

# 補足：Repository 層は本当に必要か（正直な話）

Laravel コミュニティでは **「Eloquent 自体が既に Active Record パターンの抽象化なので、その上に Repository を重ねるのは過剰では」** という議論が長年あります。フェアに両論を書いておきます。

### 割に合うケース

- **チーム開発で「クエリをどこに書くか」の統一が必要**なとき（Controller にベタ書きされる事故が消える）
- **同じ問い合わせが複数箇所で使われる**とき（`whereNull('completed_at')` の重複が消える）
- **Service の単体テストを DB なしで速く回したい**とき（STEP 10 の見返り）
- 将来的にデータソースが変わりうるとき（DB → 外部 API など）

### 割に合わないケース

- 個人開発の小規模 CRUD … Model → Controller で十分。Repository は**ファイル数が3倍になるだけ**
- Repository のメソッドが `findById` / `create` / `update` / `delete` だけ … それは Eloquent の劣化コピーです

### 現実的な折衷案

**まず Service 層だけ入れて、Repository は後から**という順序が、初学者には最も安全です。

```
Phase 1: Controller → Model            （学習中・プロトタイプ）
Phase 2: Controller → Service → Model  （チーム開発の入り口）
Phase 3: Controller → Service → Repository → Model  （規模が育ったら）
```

Phase 2 の時点で Service にクエリが集まっているので、**Phase 3 への移行は「Service からクエリを切り出すだけ」**になります。最初から3層を作るより、この順で育てるほうが「なぜこの層が必要か」を体感として理解できます。
